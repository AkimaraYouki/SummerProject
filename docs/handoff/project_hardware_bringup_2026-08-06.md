| 관절 | ID | 부호 | | 관절 | ID | 부호 |
|---|---:|---:|---|---|---:|---:|
| left_hip_yaw | 3 | **−1** | | right_hip_yaw | 1 | **−1** |
| left_hip_roll | 8 | −1 | | right_hip_roll | 4 | +1 |
| left_hip_pitch | 9 | −1 | | right_hip_pitch | 5 | +1 |
| left_knee | 10 | +1 | | right_knee | 6 | −1 |
| left_ankle | 11 | +1 | | right_ankle | 7 | −1 |
| neck_pitch | 2 | −1 | | head_pitch | 12 | +1 |
| head_yaw | 13 | −1 | | head_roll | 14 | −1 |

전부 실기에서 눈으로 확인했다(`confirmed: true`). 저장 위치:

| 파일 | 역할 |
|---|---|
| `source/open_duck_mini_isaaclab/hardware_map.py` | **단일 진실원천.** `DXL_ID` / `OFFSET_TICK` / `SIGN` / `to_ticks()` / `to_rad()` / `limit_ticks()` |

`to_ticks()` 는 **축별로** 게이트가 걸린다 — `confirmed=false` 인 축은 예외를 던진다
(`strict=False` 로 명시하면 우회). 지금은 14축 다 확인돼서 `CALIBRATION_PENDING=False`.

### 비자명한 것

**`DXL_ID` 는 관절 순서와 전혀 다르다.** ID 1 = right_hip_yaw, 2 = neck_pitch,
3 = left_hip_yaw … `ID = 인덱스+1` 로 가정하면 안 된다. 실제로 그렇게 가정했다가
3축을 가동범위 밖으로 명령해 기구 스토퍼에 밀어붙였다(최대 73.7° 오차). 하드웨어
이상이 아니라 **명령이 틀렸던 것**이다.

**hip_yaw 만 좌우가 같은 부호(둘 다 −1)** 다. 나머지 네 쌍은 전부 좌우 반대다.
URDF 상으로도 hip_yaw 는 좌우 축이 **둘 다 (0,0,−1) 로 같은 유일한 쌍**이라
앞뒤가 맞는다. 다른 쌍의 패턴으로 추론했으면 틀렸을 축이다.

**`MIRROR_SIGN` 의 hip_roll = +1 이 맞다.** `project_hardware_joint_calibration.md`
가 유일하게 미결로 남긴 항목이었는데(MIRROR_SIGN 은 좌우 같은 부호, READY 는 반대
부호), 몸통 프레임까지 변환을 합성해 보니 hip_roll 축이 좌 (+1,0,0) / 우 (−1,0,0) 로
**물리적으로 반대**다. 축이 반대인데 각도가 같으면 두 다리가 대칭으로 벌어진다 —
MIRROR_SIGN=+1 과 정확히 일치한다. READY 의 좌 +0.0213 / 우 −0.0092 는 미러쌍이
아니라 **레퍼런스 보행 자체의 좌우 비대칭 잔차**다(§5 참조).

### 몸통 프레임: **+x 가 앞이다** (2026-08-06 정정)

> ⚠️ 이 절은 원래 "**−x** 가 앞" 이라고 적었다. **틀렸다.** 아래는 정정본이다.
> 근거였던 "머리를 +45° 세우면 CoM 이 x 로 −8.8 → −23.1 mm 가고 로봇이 앞으로
> 넘어졌다" 에서 CoM 이동량 자체는 재현된다(−14.26 mm, pinocchio). 하지만 그
> 전도는 **정적 전복이 아니라 정책이 무너진 동적 결과**라 방향 판정의 근거가
> 되지 못한다. 발 지지면은 x 로 −75.3 … +28.7 mm 인데 CoM 은 −20.3 → −34.6 mm 로
> 옮겨갈 뿐 지지면을 벗어나지도 않는다.

`onshape-to-robot` 이 회전축을 로컬 Z 로 고정하므로 `axis` 는 14개가 전부 `0 0 1`
이고 부호 정보가 없다. 실제 축은 `<origin rpy>` 에 있는데, 그건 **각자의 부모 링크
프레임** 기준이라 좌우 비교가 안 된다. 루트까지 변환을 합성해야 한다.

**몸통 프레임 = +x 앞 / +y 좌 / +z 위** (표준 오른손 프레임). 독립적으로 두 번 쟀다:

1. **디딤발 흐름.** 전진 명령(vx=+0.15)에서 디딤발이 몸통 기준 x 로 **−29.8 mm**
   흐른다 — 발이 지면에 고정돼 있으니 몸통이 +x 로 전진한다는 뜻이다. 후진
   명령에서는 **+42.9 mm** 로 정확히 뒤집힌다. 크기도 0.15 m/s × 접지 0.378 s
   = 56.7 mm 와 같은 자릿수다.
2. **발 형상.** 발목 프레임 기준으로 발이 +x 로 **63.8 mm**, −x 로 **40.1 mm**
   뻗는다 — 발가락이 앞, 뒤꿈치가 뒤인 정상 형상.

좌우는 URDF 로 자명하다: `left_foot` y = **+90.9 mm**, `right_foot` y = **−91.7 mm**.

아래 표는 URDF FK 로 직접 재서(관절에 +0.4 rad 을 주고 대상 프레임의 로컬 축이
어느 쪽으로 도는지) 다시 쓴 것이다:

| 관절 | 몸통프레임 축 | URDF + 방향이면 | 예전 표 |
|---|---|---|---|
| left_hip_roll | (+1,0,0) | 왼다리가 바깥(좌)으로 벌어짐 | 같음 |
| right_hip_roll | (−1,0,0) | 오른다리가 바깥(우)으로 벌어짐 | 같음 |
| left/right_hip_yaw | (0,0,−1) | 둘 다 발끝이 **오른쪽**으로 | "왼쪽" |
| neck_pitch | (0,−1,0) | 목이 **뒤로 젖혀짐** | "앞으로 숙여짐" |
| head_pitch | (0,+1,0) | 코끝이 **아래로** | "위로" |
| head_yaw | (0,0,+1) | 고개가 **왼쪽**으로 | "오른쪽" |
| head_roll | (−1,0,0) | 머리 꼭대기가 왼쪽으로 | 같음 |

**부호(`joint_calibration.json`)는 이 정정의 영향을 받지 않는다.** 사용자가 실기를
눈으로 보면서 축마다 직접 맞춘 값이라 14축 전부 그대로 유효하다(confirmed). 바뀐
것은 "URDF + 가 물리적으로 무엇인가" 를 적은 **설명 문구뿐**이고,
`scripts/hw/joint_cal.py` 의 `EXPECT` 도 같이 고쳤다.

이 프레임 정의는 이제 `source/open_duck_mini_isaaclab/imu_map.py` 가 단일 진실원천이다.

## 2. 만든 도구

전부 Jetson 홈(`~/`)에도 복사돼 있다.

| 파일 | 용도 |
|---|---|
| `scripts/hw/joint_cal.py` | 부호 확인 대화형 도구. `d` 키로 URDF + 방향 왕복 후 `c`/`s` |
| `scripts/hw/goto_ready.py` | READY 자세 이동. smoothstep 보간, 로컬 스톨 감지 |
| `~/home_position.py` (Jetson) | 전축 2048 정렬, `--release` 로 토크 해제 |

### 안전 설계 — 이유가 있다

**전류 제한이 1차 보호다.** Operating Mode 5(전류제한 위치제어) + Goal Current
(주소 102, **RAM**)로 건다. Mode 3 에서는 Current Limit 이 EEPROM 이라 런타임 조절이
안 된다. 조그는 250 unit(0.67 A), 자세 이동은 400 unit(1.08 A)으로 충분했다.
스톨 전류가 2.3 A 이므로 관절이 걸려도 밀어붙이지 못하고 그냥 진다.

**스톨 감지는 Jetson 안에서 돈다.** 사용자가 원격 에이전트에게 "멈춰" 를 보내면
왕복 지연 때문에 늦는다(실제로 한 번 겪었다). `goto_ready.py` 는 추종 오차가
임계를 넘은 채 1초를 넘기면 스스로 전 축 목표를 현재 위치로 덮어쓴다.

`joint_cal.py` 는 **TTY 가 아니면 실행을 거부한다.** 관찰이 필요한 작업이라 사용자가
직접 돌려야 하고, 에이전트가 대신 돌리면 안 되기 때문이다.

## 4. 통신 성능 — 여기가 다음 벽

정책 사양: **50 Hz**(`decimation=10 × sim dt 0.002 = 0.02 s`), 관측 101차원
(v33 계열은 path 3 + gravity 3 붙어 107), 액션 14.

101차원 중 **서보 버스에서 와야 하는 건 `joint_pos` 14 + `joint_vel` 14 뿐**이다.
나머지는 IMU(6), 사용자 명령(7), 내부 상태(last_act ×3 = 42, motor_targets 14),
발 접촉(2), 위상(2).

### 실측 (57600 baud, Jetson, latency_timer=16)

| 트랜잭션 | 시간 |
|---|---:|
| SyncRead 위치만 4B @132, 14축 | 64.1 ms |
| **SyncRead 전류+속도+위치 10B @126, 14축** | **80.0 ms** |
| SyncRead 속도만 4B @128, 14축 | 64.0 ms |
| SyncWrite 목표위치 4B @116, 14축 | 12.8 ms |

**정책 1회 = 80.0 + 12.8 = 92.8 ms → 10.8 Hz.** 필요한 50 Hz 의 **1/4.6** 이다.

**Present Current(126) / Velocity(128) / Position(132) 은 연속이다.** 주소 126 에서
10바이트를 한 번에 읽으면 속도와 위치가 같이 온다. 따로 읽으면 140.9 ms(7.1 Hz),
합쳐 읽으면 92.8 ms — **48 ms 절약**. 읽기 트랜잭션 하나가 통째로 사라진다.

### 병목은 두 개고 성격이 다르다

축 수를 바꿔가며 재면 분리된다:

| 축수 | SyncRead | SyncWrite |
|---:|---:|---:|
| 1 | **16.07 ms** | 2.47 ms |
| 2 | 16.91 ms | 3.26 ms |
| 4 | 32.20 ms | 5.02 ms |
| 8 | 48.04 ms | 8.28 ms |
| 14 | 64.25 ms | 13.38 ms |

- **SyncWrite 는 축당 0.84 ms 로 선형** — 순수 보드레이트 항이다(응답을 안 기다린다).
- **SyncRead 는 16 ms 배수로 계단처럼 뛴다.** 축이 1개뿐인데 16.07 ms 인 게 결정적이다.
  데이터는 1 ms 도 안 되는데 16 ms 가 걸렸다 — **FTDI `latency_timer=16`** 에 물린 것.

### 그래서 필요한 것

| 설정 | 읽기 | 쓰기 | 루프 | |
|---|---:|---:|---|---|
| 현재 (57600, lat 16) | 80 ms | 13 ms | **10.8 Hz** | |
| 57600 + lat 1 | ~55 ms | ~13 ms | ~15 Hz | 부족 |
| 1 Mbps + lat 16 | ~16–32 ms | ~1 ms | 30–59 Hz | 아슬아슬 |
| **1 Mbps + lat 1** | ~3 ms | ~1 ms | **~250 Hz** | 여유 |

**보드레이트만 올리면 50 Hz 에 걸친다.** latency timer 16 ms 양자가 남아서 한 프레임이
양자에 걸리면 바로 20 ms 예산을 넘긴다. **둘 다 해야 한다.**

1. **`latency_timer` → 1.** 호스트 설정이라 모터를 안 건드리고 되돌리기 쉽다.
   root 소유라 sudo 필요:
   `echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyUSB0/latency_timer`
   **재부팅하면 16 으로 돌아간다** — 영구화하려면 udev 룰이 필요하다. 아직 안 했다.
2. **보드레이트 → 1 Mbps.** EEPROM(주소 8) 쓰기라 성격이 다르다. 14축 중 일부만
   성공하면 축마다 보드레이트가 갈려 다시 찾아야 하니, 실패해도 복구되게 스캔을
   붙여서 할 것. 4.5 Mbps 는 1 Mbps 대비 이득이 작다(다른 항이 이미 지배적).

**줄일 여지 하나 더**: 머리 4축은 `lock_head_joints=True` 라 정책이 제어하지 않는다.
관측의 `joint_pos`/`joint_vel` 중 머리 4개는 고정값이므로 읽지 않고 채워도 된다.
읽기 대상 14 → 10축이면 약 30% 절약. 보드레이트를 올린 뒤에 의미 있는 수준이다.

**참고: 개루프면 지금도 70 Hz 가 나온다.** 읽기를 빼고 쓰기만 하면 `goto_ready.py`
가 3.02초에 212루프(70 Hz)를 돌았다. 궤적이 미리 정해진 이동에는 쓸 수 있지만
**정책에는 못 쓴다** — 관절 상태 피드백이 관측에 들어가기 때문이다.

## 5. IMU — ~~달려 있지만 꺼져 있다~~ → **깨웠고 축맵도 실측 완료** (2026-08-06 갱신)

> ✅ **해결됨.** NDOF 로 깨워서 출력이 나온다. 장착 축맵은 **항등** — 칩이 몸통
> 축에 정렬돼 붙어 있다(세 자세 실측, 잔차 0.078, 축별 최대 기울기 4.64°).
> 도구 `scripts/hw/imu_check.py` (`--probe` / `--calibrate` / `--verify`),
> 결과 `source/open_duck_mini_isaaclab/imu_calibration.json`,
> 규약과 상수는 `source/open_duck_mini_isaaclab/imu_map.py`.
>
> **같이 발견한 결함**: 시뮬 `ImuCfg.offset` 이 **원본 Open Duck Mini 의 MJCF 에서
> 복사한 값**(−80, 0, +50 mm)이었다. 이 로봇의 CAD 값은 (−38.8, 0, +91.4) mm 로
> x·z 각각 41 mm 다르다. `IMU_MOUNT_POS` 로 고쳤다 — **관측이 바뀌므로 그 이전
> 체크포인트와는 호환되지 않는다.**
>
> **남은 것**: `OPR_MODE` 는 휘발성이라 전원을 껐다 켜면 CONFIG 로 돌아간다.
> 정책 실행 스크립트가 시작할 때 NDOF 로 올리는 초기화를 넣어야 한다.
> `AXIS_MAP_CONFIG`(0x41)/`AXIS_MAP_SIGN`(0x42) 는 칩 기본값 0x24/0x00 그대로
> 두었다 — 축맵이 항등이라 굽을 필요가 없고, 어차피 전원 끊기면 날아간다.

**BNO055, `i2c-7` 주소 `0x28`.** CHIP_ID 0xA0 / ACC_ID 0xFB / MAG_ID 0x32 /
GYR_ID 0x0F — 전부 데이터시트 값과 일치, 확정이다.

> ⚠️ **`OPR_MODE`(0x3D) = 0x10.** 하위 4비트만 유효하므로 마스크하면 **0x00 = CONFIG
> 모드**다. 즉 **센서 출력을 내지 않는 상태**다. `CALIB_STAT`(0x35) = 0x00 인 것도
> 그 때문. 통신 속도를 아무리 올려도 이 상태로는 정책이 못 돈다.

### 읽기 실측 (I2C 100 kHz)

| 읽기 | 시간 |
|---|---:|
| accel 6B (0x08) | 1.95 ms |
| gyro 6B (0x14) | 1.95 ms |
| **accel + gyro, 2회** | **3.89 ms** |
| accel+mag+gyro 연속 18B | 4.51 ms |
| gravity vector 6B (0x2E) | 1.94 ms |

**연속 18B 가 오히려 느리다** — 중간의 mag 6바이트가 필요 없는데 같이 읽힌다.
따로 두 번 읽는 게 맞다. 6바이트에 1.95 ms 면 버스가 **100 kHz(표준 모드)** 다.
400 kHz 로 올리면 1 ms 아래로 내려간다. 다만 4 ms 는 20 ms 예산의 20% 라
서보 통신(93 ms)에 비하면 급하지 않다.

### 모드 선택이 남아 있다

- **AMG (0x07)** — 원시 가속도/자이로/지자기. 시뮬 `Imu` 센서와 성격이 같다.
- **NDOF (0x0C)** — 융합. 원시값도 그대로 나오면서 **중력 벡터(0x2E)** 를 직접 준다.

**NDOF 를 권한다.** v33 계열이 `use_gravity_obs=True` 라 `projected_gravity` 3차원이
필요한데, 이걸 가속도에서 직접 만들면 가속 중에 틀린다. 단 NDOF 는 지자기
캘리브레이션이 필요하고 실내 자기 왜곡을 탄다 — 문제가 되면 IMU 모드(0x08,
지자기 제외 융합)가 대안. `OPR_MODE` 는 EEPROM 이 아니라 런타임 레지스터라
전원을 껐다 켜면 CONFIG 로 돌아간다.

**반드시 맞춰야 하는 것: `AXIS_MAP_CONFIG`(0x41) 이 몸통 프레임과 일치해야 한다.**
몸통 프레임은 **−x 가 앞**이다(§1). 센서가 어떤 자세로 붙어 있느냐에 따라 리맵이
필요하고, 이건 아직 확인하지 않았다.

## 6. 시뮬 쪽에서 발견한 결함 3개 — **아직 안 고쳤다**

실기 이식 전에 닫는 게 맞다. 이 세션에서는 **검증 환경이 없어 손대지 않았다**
(사용자 데스크탑에 torch / Isaac Sim 미설치, 수정해도 돌려볼 수 없었다).

### (a) v33 ZNeck 의 `head_pitch` 가 하드 리밋 위에 앉아 있다

```
head_pitch  READY(ZNeck) +0.7850 rad (+45.0°)
            URDF hard    [-0.7854, +0.7854]   ← 0.0004 rad 남음
            soft (0.95)  [-0.7461, +0.7461]   ← 2.2° 초과
            리셋 지터 ±0.05 → 최대 0.835      ← 하드 리밋 밖
```

14축 중 유일하게 소프트 리밋을 넘는다. `lock_head_joints=True` 라 액션이 0 으로
고정되니 목표가 매 스텝 0.785 로 유지되고 PD 가 계속 리밋에 밀어붙인다.
**0.746 (42.7°) 으로 낮추면** 지터까지 포함해 하드 리밋 안에 들어온다. 머리를
수평으로 유지하는 게 목적이면 neck/head 둘 다 0.746 으로(둘이 같은 부호로 상쇄).

### (b) RSI 스폰의 **8.05%** 가 관절 하드 리밋 밖에서 시작한다

RSI 는 다리 10축을 레퍼런스 프레임으로 덮어쓰는데(`_reset_idx`, joystick_env.py),
레퍼런스 자체가 URDF 한계를 넘는다. 명령 랜덤 × 위상 랜덤 20,000 샘플:

| 관절 | hard 초과 | soft 초과 |
|---|---:|---:|
| right_knee | **4.50%** | 10.66% |
| right_hip_pitch | **2.28%** | 7.75% |
| left_hip_pitch | **1.75%** | 5.71% |
| left_knee | 0.00% | 6.60% |

**한 관절이라도 하드 리밋 밖에서 스폰: 8.05%.** `write_joint_state_to_sim` 이 그
값을 그대로 쓰므로 PhysX 가 리셋 직후 관절을 되민다 — `SPAWN_BASE_HEIGHT` 주석이
기록한 "스폰 순간 튕김" 과 같은 계열의 교란이 관절 쪽에도 있는 것이다.
레퍼런스를 URDF 한계로 클립하거나 리셋에 `joint_pos.clamp(soft_limits)` 한 줄.

### (c) 레퍼런스 보행이 좌우 비대칭이다

`ref_h175.pkl`, 명령 8종 × 주기 27스텝:

```
left_knee  범위 [-2.072, -1.436]  →  |크기| 1.436 ~ 2.072
right_knee 범위 [+1.443, +2.174]  →  |크기| 1.443 ~ 2.174   ← 0.10 rad(5.9°) 더 깊다
left_hip_pitch  최대 1.2285
right_hip_pitch 최대 1.2698                                  ← 0.041 rad 더 크다
```

미러 대칭이면 크기가 같아야 한다. **right_knee 만 하드 리밋을 넘는 이유가 이것**이고,
이 프로젝트 최대 결함으로 기록된 횡방향 오차와 같은 방향을 가리킨다. v29(좌우 미러
손실)가 정책 쪽에서 고치려다 이득이 없었는데, **원인이 정책이 아니라 레퍼런스 생성
쪽**일 가능성이 있다. 레퍼런스 재생성이 필요한 별건이다.

> 참고: READY(H175) 자체는 액션 도달성 기준으로 건강하다. 레퍼런스 평균과의 차이가
> 전 관절 0.21° 이내이고, 보행 진폭을 덮는 데 필요한 최대 액션은 **1.49**(right_knee)
> — v1~v9 를 죽인 8.1 대비 여유가 크다.

## 8. 함정 — 같은 데서 두 번 넘어지지 말 것

- **`/dev/ttyUSB0` 이 있어도 모터 전원과는 무관하다.** U2D2 는 USB 로 켜지므로
  배터리가 꺼져 있어도 포트가 정상적으로 열리고 FT232H 도 lsusb 에 보인다.
  살아있는지는 **핑을 쳐야만** 안다. 전 보드레이트(9600~4M)를 훑어서 0개면
  통신 설정이 아니라 전원/배선 문제다.
- **ID 순서를 가정하지 말 것.** §1 참조.
- **ssh 세션이 끊기면 SIGHUP 으로 즉시 죽어 `finally` 가 안 돈다.** 이걸로 캘리브레이션
  한 세션치를 통째로 날렸다. `joint_cal.py` 는 이후 SIGHUP/SIGTERM 을 잡고,
  상태가 바뀌는 모든 키에서 즉시 저장하며, 임시파일→rename 으로 원자적으로 쓴다.
- **원격 에이전트에게 "멈춰" 를 보내면 늦는다.** 안전 정지는 Jetson 안에서 돌아야 한다.
- **머리 4축을 0 이 아닌 값으로 두려면 그 자세로 재학습해야 한다.** 자세만 바꾸면
  무게중심이 14.3 mm 옮겨가 넘어진다(v33 이 그 시도, iter 663 에서 중단).
