## 이 프로젝트에서 실제로 통했던 것

리워드 계수는 열 번 넘게 만졌지만 매번 국소 개선에 그쳤다. 판을 바꾼 것은
전부 **구조**였다:

1. **액션 도달성** (v1~v9 실패의 원인) — `default_joint_pos`가 HOME(전부 0)이라
   레퍼런스가 요구하는 무릎 2.03 rad에 닿으려면 액션 8.12, 즉 `init_noise_std=1.0`
   기준 8σ 밖이었다. 탐험으로 도달 불가능. READY 자세 도입으로 해결.
2. **비대칭 크리틱** — 크리틱이 정책과 같은 노이즈 섞인 101차원만 봤다.
   시뮬만 아는 정보(실제 속도·토크·레퍼런스 전체)를 205차원으로 주니
   **리워드를 한 글자도 안 바꾸고 스텝당 3배.**
3. **gamma 0.99 → 0.97** — 유효 시간지평 100스텝 → 33스텝. 보행 주기가
   27스텝이니 한 주기. +53%.
4. **path frame** — 명령이 순수 rate라 "휘었다"를 정책이 관측할 수 없었다.
   적분된 경로 대비 횡방향·방향 오차를 관측에 넣어 직진성 확보.

**공통점: 리워드를 정교하게 만드는 것보다 가치 추정과 관측을 고치는 것이
훨씬 크게 작용했다.** 리워드 튜닝에 손이 갈 때 한 층 위를 먼저 보라.

## 반복해서 겪은 함정

- **스케일 착시** — 버전마다 리워드 항이 달라 스텝당 절대값 비교가 무의미하다.
  리워드가 동일할 때만 직접 비교하고, 아니면 행동 지표(속도·관절오차·토글)로 판단.
- **한 번에 하나만** — v22와 v20b를 "minibatch 차이"로 설명했다가 v23에서
  틀렸음이 드러났다. 실제로는 다섯 개가 함께 달랐다.
- **하이퍼파라미터는 구현 간에 이식되지 않는다** — brax의 `num_minibatches=32`가
  rsl_rl에서는 iteration당 128회 업데이트가 되어 KL이 초과하고 adaptive lr이
  1e-5 바닥까지 깎였다.
- **경로의 공백** — `/media/.../Extreme SSD`의 공백이 `$(ls)`·`xargs basename`을
  단어 분리시켜 여러 번 깨졌다. glob이나 `while read`를 쓸 것.
- **Isaac Sim 두 개 동시 실행 금지** — 한쪽이 조용히 죽는다. `odm`이 자동으로 막는다.

## 미해결

- **좌측 이동 비대칭** — 횡 이탈 좌 247 mm vs 우 143 mm. 발 태스크스페이스에서
  오른발이 왼발보다 22% 크게 움직이는 것과 같은 뿌리일 수 있다.
- **다리-몸통 접촉** — 정확 메시 기준 레퍼런스는 접촉 0%인데 정책은 56.7%.

- **다지형** 미착수, **실기 이식(ONNX)** 미착수.

## 갱신 (2026-07-30, 위의 두 가지를 실제로 파본 결과)

**2번은 해결됐다.** 원인은 저장된 `params/`가 아니라 **rsl-rl 자체가 세대를
건너뛴 것**이었다. 랩PC는 isaaclab_rl 0.2.0 + rsl-rl 2.x, 이 PC는 0.5.1 +
**rsl-rl 5.0.1**이다. SSD는 따라왔지만 IsaacLab은 각 기계 홈에 따로 깔려 있어
따라오지 않았다. 끊긴 곳은 세 군데:

- 설정 스키마: `policy` 하나 -> `actor`/`critic` + `obs_groups`
- 체크포인트: `model_state_dict` 한 덩어리(정규화기는 러너 밖)
  -> `actor_state_dict`/`critic_state_dict`(정규화기는 모델 안)
- wrapper의 `get_observations()`가 튜플이 아니라 TensorDict를 돌려준다

`source/.../agents/rsl_rl_compat.py`가 셋을 다 흡수한다. 설정은 계속 `policy`로
적고 상류의 `handle_deprecated_rsl_rl_cfg`에 변환을 맡기므로, 두 세대의 rsl-rl
어디서든 뜬다. 체크포인트 변환은 Isaac 없이 도는 테스트로 덮여 있다
(`tests/test_rsl_rl_checkpoint_conversion.py`).

확인된 것: `odm measure v25`가 위 표의 수치를 재현하고(전진만 0.138~0.159로
흔들리는데 두 번 재보니 런간 편차 범위다), `odm train`도 이 PC에서 돈다 —
액터 104->512, **크리틱 208**->512로 비대칭 크리틱이 그대로다.

**1번도 해결됐다 — 원인은 NVIDIA 드라이버였다.**

`nvidia-driver-595-open` **595.84**가 Isaac Sim의 RTX 렌더러를 깬다. **580.173.02**로
내리니 그대로 돌아왔다. Isaac Sim도 IsaacLab도 건드릴 필요가 없었다.

    안 됨:  595.84
    됨:    580.173.02   (랩PC는 570.211.01, 역시 정상)

**이걸 잡아준 것은 랩PC와의 비교 한 번이었다.** 랩PC(`do@192.168.137.111`)는
**같은 RTX 5080**, 같은 커널(6.8.0-124), 같은 Ubuntu 22.04.5에서 렌더러가 멀쩡했다.
결정적으로, 랩PC의 *정상 동작하는* 렌더러 바이너리(`libnrend.so`)는 GPU 아키텍처
목록(최대 sm_90)과 번들 CUDA(11.8)가 이 PC와 **완전히 동일**했다. 같은 바이너리가
같은 GPU에서 한쪽만 죽으면 남는 변수는 드라이버뿐이다.

혼자 파는 동안 세운 가설은 **전부 틀렸다.** 다음 사람이 다시 밟지 않도록 남긴다:

- IOMMU — 아니다. `intel_iommu=off`로 재부팅해도 똑같이 죽었고, 지금은 IOMMU가
  켜진 채로 잘 돈다. (NVIDIA가 띄우는 IOMMU 경고문은 이 증상과 무관하다.)
- 렌더러에 Blackwell(sm_120) 코드가 없어서 — 아니다. 랩PC도 sm_90까지뿐이다.
- IsaacLab 설정 / experience(.kit) — 아니다. Isaac Sim 자체 GUI도 같이 죽었다.
- 셰이더 캐시, ROS `LD_LIBRARY_PATH`, 창(X)/디스플레이, GPU 메모리 — 전부 아니다.
- Isaac Sim 6.0.1 + IsaacLab v3 베타로 통째 업그레이드 — **필요 없다.** 랩PC는
  오히려 더 낮은 Isaac Sim 5.0.0-rc.45로 잘 돌고 있다.

**교훈: 되는 기계가 하나라도 있으면 거기부터 비교하라.** 크래시 로그를 아무리
파도 "같은 바이너리인데 한쪽만 죽는다"는 사실 하나를 못 이긴다.

(이하 옛 기록 — 위 결론이 나오기 전의 조사 내용)

**1번은 이 프로젝트 문제가 아니다.** "2번이 1번의 원인"이라는 위의 추정은
틀렸다. 프로젝트 코드를 한 줄도 안 쓰는 `AppLauncher(headless=False)` 세 줄로도
똑같이 죽고, 자리도 매번 같다 (`omni.usd.create_hydra_engine` ->
`librtx.scenedb.plugin.so`). 제외한 것: 샌드박스, ROS `LD_LIBRARY_PATH`,
셰이더 캐시, 드라이버 미지원 범위, 그리고 **창 자체** — `headless=True,
enable_cameras=True`로 창 없이 RTX만 켜도 같은 자리에서 죽는다. 즉 WebRTC로도
우회되지 않는다. 이 PC의 Isaac Sim 설치(소스 빌드
`~/Desktop/issacsimfolder/isaacsim/_build/...`, IsaacLab의 `_isaac_sim`이 그리로
심링크) 쪽을 봐야 한다. 재현용 최소 스크립트를 먼저 쓸 것 — 부팅이 2.5초라
반복이 싸다.

    from isaaclab.app import AppLauncher
    app = AppLauncher(headless=True, enable_cameras=True).app

**학습은 막혀 있지 않다.** 학습은 원래 `--headless`라 렌더러를 안 쓴다.
1번이 막는 것은 눈으로 보는 것(`odm play`)뿐이고, 측정(`odm measure`)은 된다.
다만 이 프로젝트의 결정적 단서는 매번 육안 관찰에서 나왔으므로, v25를 3000까지
미는 것과 1번을 고치는 것 중 무엇을 먼저 할지는 그 점을 감안해서 정할 것.

# 2026-07-30 야간 실험 (v26~v29)

## 결론부터

**현재 최고: `imitation_v28` 의 `model_1500.pt`** — 평균 명령 추종 오차 **0.0153**.
`odm list` 로 런 디렉터리를 찾을 것 (`..._imitation_v28`).

측정은 잡음이 커서 **버전마다 2회씩** 쟀다. 명령별 오차는 표본당 ±0.02 로
흔들리므로 한두 번 측정으로 특정 명령을 논하면 안 된다.

| 실험 | 바꾼 것 (한 번에 하나) | 평균 추종 오차 | 판정 |
|---|---|---|---|
| v26@1500 | v25 를 새 rsl-rl 에서 재현 (기준선) | 0.0250 | 기준 |
| v27@1500 | 정책 관측에 중력 방향 3차원 | 0.0202 | 개선 |
| v27@2000 | (더 학습) | 0.0213 | 악화 |
| **v28@1500** | **로봇 키 +12% (레퍼런스 재생성)** | **0.0153** | **최고** |
| v28@2000 | (더 학습) | 0.0160 | 악화 |

| v30 | 로봇 키 +27% (0.19) | 진행 중 | — |

**v28 이 유일하게 명확한 개선이다.** 키를 올리자 이 프로젝트 최대 결함이던
횡방향 오차가 절반이 됐다 (좌 0.040 -> 0.017, 우 0.035 -> 0.018; 각 4표본으로
구간이 겹치지 않는다). **왜 그런지는 모른다** — 바꾼 건 키뿐인데 좌우가 좋아졌다.

v29(미러 손실)는 같은 표적을 노렸으나 실패했다. 추측: 미러 손실이 멈춘 값을
관절각으로 환산하면 0.03 rad 인데 레퍼런스 자체의 좌우 잔차가 0.02~0.05 rad 다.
**강제할 대칭이 애초에 데이터에 없었다.** 확인하려면 레퍼런스를 좌우 평균으로
대칭화해서 다시 생성해 봐야 한다 (미착수).

## 반복해서 확인된 것 — 오래 학습하면 나빠진다

    v25@1500  >  v26@2999
    v27@1500  >  v27@2000

두 번 다 같은 방향이다. **이 리워드 구조에서는 학습을 오래 할수록 명령 추종을
잃는다.** v26 은 리워드 곡선이 평평해진 뒤에도 행동이 계속 나빠지고 있었다 —
**리워드 수렴은 행동 수렴이 아니다.** 그래서 새 실험은 반드시 1500 과 최종을
둘 다 재고, 비교는 **같은 iteration 끼리** 한다 (`odm measure <ver> <iter>`).

## %가 아니라 오차로 봐라

v26@1500 은 전진 0.169 로 **오버슈트**해서 "명령의 113%"가 된다. %로 보면
v25 의 89% 보다 좋아 보이지만 실제로는 오차가 더 크다. `gait_compare` 가
출력하는 `err` 를 쓸 것.

## 이번에 실제로 밟은 함정들

- **v27 의 기전 설명은 확정이 아니다.** 중력 관측이 몸통을 잡아줄 것이라 보고
  넣었는데, 추종은 22% 좋아졌지만 몸통 roll 은 6% 만 줄고 pitch 는 오히려
  23% 나빠졌다. 결과는 실측이지만 "왜" 는 아직 모른다.
- **안착 높이는 스폰이 낮으면 측정 자체가 오염된다.** v28 준비 중 스폰을
  그대로 두고 쟀더니 안착값이 92~188 mm 로 흩어졌는데, 최댓값이 스폰보다
  높아 중력만으로 불가능한 값이었다 — 발이 지면을 파고들어 PhysX 가 튕겨낸
  것이다. 충분히 높은 데서 떨어뜨려야 한다 (`scripts/diag/settle_height.py`).
- **좌우 미러를 가정으로 짜면 틀린다.** 이 URDF 는 좌우 관절 축이 대칭이
  아니다(같은 자세에서 left_knee -1.785 vs right_knee +1.816). 순진한
  "roll/yaw 부호 반전"은 hip_roll / knee / ankle 세 관절이 틀린다.
  `scripts/diag/derive_mirror.py` 가 레퍼런스 데이터에서 유도한다.
- **보행 주기가 27 로 홀수라 "반 주기"가 정수가 아니다.** 미러 유도에서
  13 으로 자르니 잔차가 남았고, 13.5 로 보간하니 사라졌다.
- **v28 은 다른 레퍼런스를 모방한다.** 그래서 v27 과의 리워드 총합 비교는
  무의미하다("스케일 착시"의 변종). 판정은 레퍼런스와 무관한 `odm measure` 로만.

## 로봇 키를 바꾸려면

손잡이는 medium 프리셋의 `walk_com_height` 다 (`fast.json` 은 안 쓰인다).
**레퍼런스부터 다시 만들어야 한다** — 서는 높이는 레퍼런스 보행의 평균
자세에서 나오므로, READY 자세만 높이면 모방 리워드가 되돌리고 액션이 도달
불가능해진다 (v1~v9 실패 원인). 전체 절차는 `docs/map.md` 의
"레퍼런스 보행을 새로 만들 때" 절.

이 PC 에는 placo 를 못 깐다 — 랩PC 에서 원격으로 돌린다
(`scripts/setup/gen_reference_remote.sh`).
