# 실기가 심의 42 % 토크로 돌고 있었다 — 그리고 goto_ready 의 2배 오류

2026-08-12. 계기: "왼무릎이 보행 중 목표보다 22~32도 더 접힌 채 끌려다니고,
앞으로 꼬구라진다." 하드웨어 시험은 두 번 다 통과해서 (주파수 응답 이득
0.95~1.00 / 좌우차 2 % 이내, 손으로 몸통 들고 보행하면 정상 추종) 모터
자체는 무죄로 판명된 상태였다. 남은 후보가 서보 **설정** 이었다.

`scripts/hw/dump_ctrl_table.py` 로 14축 EEPROM+RAM 을 처음 전부 덤프했다.

## 1. 서보 설정은 무죄 — 좌우 완전 동일

| 항목 | 값 (다리 10축 전부 동일) |
|---|---|
| Position P / I / D Gain | 800 / 0 / 4700 |
| Velocity P / I Gain | 100 / 1920 |
| Feedforward 1st / 2nd | 0 / 0 |
| Drive Mode | 0 (정방향, 시간기반 프로파일 꺼짐) |
| Operating Mode | 5 (전류기반 위치제어) |
| Homing Offset | 0 |
| Min / Max Position Limit | 0 / 4095 (EEPROM 클램프 없음) |
| Profile Velocity / Acceleration | 0 / 0 (제한 없음) |
| PWM Limit | 885 (100 %) |
| Shutdown | 52 = 과열+전기충격+과부하 |
| Return Delay Time | 250 (= 500 us) |

**좌우로 다른 설정값은 하나도 없다.** 유일한 차이는 펌웨어 버전 (44 / 48 /
49 / 50 이 섞여 있다) 인데 무릎 두 축은 그마저 둘 다 44 다. 왼무릎 처짐의
원인은 서보 설정이 아니다.

## 2. Goal Current 350 — 심이 가정한 값의 절반

덤프에서 **Current Limit = 350 틱 = 0.9415 A** 가 나왔다. `rl_walk.py
--current` 기본값이 350 이었다.

`robot_cfg.py` 의 토크 모델은 ROBOTIS 성능그래프에서 뽑은 τ = 1.96·(I − 0.27):

| | 전류 | 관절 토크 |
|---|---|---|
| 심이 전제한 값 (`XM430_CONT_TORQUE_700`) | 1.883 A (700 틱) | **3.16 N·m** |
| 실기 실제 (v41~v46 전 기간) | 0.9415 A (350 틱) | **1.32 N·m** |

**실기는 심이 허용한 토크의 42 % 로 돌고 있었다.** v41 이후 모든 정책
(v41·v42·v43·v44·v46) 이 `effort_limit: 3.16` 으로 학습됐다 — 정책은 무릎에
3.16 N·m 를 쓸 수 있다고 배웠는데 실기는 1.32 N·m 에서 잘렸다. 체중을 받는
순간 무릎이 밀려 내려가고 앞으로 무너지는 게 정확히 이 증상이다.

상수 이름 자체가 `XM430_CONT_**700**` 인데도 못 잡은 이유: 두 숫자가 서로
다른 파일 (`robot_cfg.py` 와 `rl_walk.py`) 에 살았고, `robot_cfg.py` 의
주석은 "실기 `rustypot_hwi.py` 의 current_limit 700 틱" 이라고 **사실과
다르게** 적혀 있었다 (실제 기본값은 350). `rl_walk.py` 독스트링에는
"다리가 실제 보행 부하를 못 버티고 멈추면(주저앉으면) --current 를 올릴 것"
이라고 적혀 있었는데, 정확히 그 증상이 났는데도 아무도 올리지 않았다.

### 고친 것

* `rl_walk.py --current` 기본값 350 → **700**.
* `export_onnx.py` 가 `params/env.yaml` 에서 다리 `effort_limit` 을 뽑아
  `policy.meta.json` 에 싣는다 (ImplicitActuator 는 `effort_limit_sim`,
  DCMotor 는 `effort_limit`. v40 이전 = 4.1, v41 이후 = 3.16).
* `rl_walk.py` 가 시작할 때 `--current` 를 **토크로 환산해서** 심의
  `effort_limit` 과 나란히 찍고, 90 % 미만이면 경고한다. 암페어만 찍던 게
  두 값을 대조하지 못한 직접 원인이었다.
* `robot_cfg.py` 주석에서 틀린 서술을 고치고, 이게 심이 실기에 요구하는
  **계약** 임을 명시.

### 대가

700 틱 = 1.88 A 는 스톨 전류 2.3 A 의 82 %. 연속으로 물리면 발열과 Overload
래치가 온다 (v42 에서 겪었다). 매 스텝 temp/hw_error 를 찍으므로 60 °C 를
넘으면 멈출 것.

## 3. goto_ready 가 목표각의 절반까지만 갔다

같은 조사에서 별개의 버그가 나왔다. 젯슨의 `goto_ready.py` 만

    TICK_RAD = 4.0 * math.pi / 4096.0      # 틀림

를 들고 있었다. XM430 은 4096 틱이 1 회전이므로 `2.0*pi/4096` 이 맞다.
같은 상수를 가진 다른 네 파일 (`rustypot_hwi` / `dxl_bridge` / `joint_cal` /
`play_ref_gait`) 은 전부 맞았다 — **표를 복제한 대가다.**

효과: 모든 목표각이 중심에서 절반으로 줄었다. v46 READY 의 무릎 −76.7° 를
명령하면 실제로는 −38.3° 에서 멈춘다 (437 틱 차이).

그 상태로 `rl_walk` 를 켜면 램프인(기본 3 초) 이 나머지 38° 를 메우면서
지면에 선 로봇을 4 cm 강제로 주저앉힌다. 순간 충격은 아니지만 (한 스텝
낙하가 아니다) 시작 자세로서는 불안정하다.

여기에 더해 `goto_ready` 의 하드코딩 READY 표는 2026-08-08 자라 v46 과
최대 25.6° 어긋나 있었다:

| 관절 | 하드코딩 | v46 READY | 차이 |
|---|---|---|---|
| left_knee | −102.28° | −76.72° | +25.56° |
| right_knee | +104.07° | +78.23° | −25.83° |
| left_ankle | +49.54° | +35.90° | −13.64° |
| right_ankle | −50.16° | −35.70° | +14.46° |
| left_hip_pitch | +56.78° | +44.85° | −11.93° |
| right_hip_pitch | +57.95° | +46.55° | −11.40° |
| neck_pitch / head_pitch | 0° | +30° | +30° |

### 고친 것

`goto_ready.py` 를 다시 썼다.

* `TICK_RAD` / `CENTER` / ID / 부호 / 관절한계 / `tick_of` 를 전부
  `rustypot_hwi` 에서 **import** 한다. 자기 사본을 안 갖는다.
* READY 기본 출처가 `policy.meta.json` 이다. `--policy` 를 생략하면
  `~/policy*/` 중 메타가 가장 최근인 것을 자동으로 고르고 어느 것을 골랐는지
  찍는다. 하드코딩 값은 `--policy -` 로만 쓸 수 있고, 메타를 쓸 때도 그
  표와의 차이를 축별로 출력한다.

검산 (v46, `--dry-run`): left_knee −76.72° → 틱 1175
= 2048 − 1.3391/(2π/4096). 버그 상태에서는 1612 였다.

## 4. 아직 못 푼 것 — 무릎 전류/PWM 이 말이 안 된다

마지막 v46 로그 (17 행, 0.36 초) 에서:

```
t=0.16  left_knee  목표 −60.0°  실제 −79.2°  오차 19.1°  PWM 1.000  전류 0.005 A  토크 ON
t=0.28  right_knee 목표 +80.2°  실제 +71.5°  오차  8.7°  PWM −0.391 전류 −1.014 A  토크 ON
```

Position P Gain 800 에서 오차 19° (218 틱) 면 PWM 이 포화되고 전류는 상한에
붙어야 한다. PWM 은 실제로 포화(±1.000)했는데 전류가 0.005 A 다. 50 Hz 샘플
하나로는 서보 내부 전류루프의 채터링과 구분이 안 되므로 **이 조합만으로는
결론을 내지 않는다.** 벤치에서 정적으로 다시 재야 한다.

같은 로그에서 `goal_*` / `pwm_*`(정규화 전 기준) / `err_*` 열이 각각
−1/1/−2, 0 같은 값으로 깨져 있다 — 로깅 쪽도 손봐야 한다.
