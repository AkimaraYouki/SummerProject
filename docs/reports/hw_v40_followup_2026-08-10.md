분석들**을 함께 남긴다.

## 1. 고친 것 — 전부 재확인됨

### 1.1 제어 스톨 (10 스텝마다 85 ms)

이전 로그에서 `step % 10 == 0` 인 루프만 **84.9 ms**, 나머지는 20.2 ms 였다
(100 초 중 25 초 손실). 원인은 그 루프에서 버스를 **4번** 읽은 것이다:

```
get_fatal_errors() -> get_hw_errors() 2회 (에러비트가 떠 있으면 재확인)
                    + 아래에서 get_hw_errors() 또 2회
hw_error SyncRead 1회 = 16.0 ms (실측)  ->  4 x 16 = 64 ms
실측 편차 84.9 - 20.2 = 64.7 ms 와 일치
```

수정: `get_hw_errors(confirm=False)` 로 루프당 read 1회, 확인은 다음 루프에서
(`fatal_pending`), 주기 10 -> 25 스텝.

**결과: 38 Hz -> 47.6 Hz, 보행주기 0.71 s -> 0.568 s (학습 0.54 s).**

### 1.2 중력 관측 (생가속도 -> 융합 출력)

`REG_ACC_DATA(0x08)` -> `REG_GRV_DATA(0x2E)`. BNO055 가 NDOF 융합으로 이미
분리해 둔 중력 벡터다. 칩에서 직접 측정:

| | 크기 평균 | std |
|---|---|---|
| ACC (0x08) | 9.746 | 0.0231 |
| GRV (0x2E) | 9.806 | **0.0000** |

| | 이전 | 이후 |
|---|---|---|
| `proj_grav` 크기 | 변동 | **1.0000, std 0.00000** |
| 피치 인접샘플 변화 평균 | 7.0° | **0.62°** |
| 최대 | 35.1° | **4.67°** |

**구현 주의 — 바꿀 칸은 하나뿐이다.** 심에서 두 칸의 출처가 다르다
(`joystick_env.py:430, 469`):

* 관측 accelerometer 3칸 = `imu.data.lin_acc_b` — 접지 충격이 들어간 센서값.
  실기도 **생 ACC 를 그대로** 써야 맞다.
* 관측 projected_gravity 3칸 = `robot.data.projected_gravity_b` — 쿼터니언
  참값, 노이즈는 ±0.1 균등뿐. **여기만** GRV.

기존 코드는 한 배열로 두 칸을 다 만들고 있었다. `--grav-src accel` 로 예전
동작 복귀 가능(A/B 용).

**미해결**: BNO055 융합이 캘리브레이션 안 됨 — `CALIB_STAT = 0x34`
(sys 0 / gyr 3 / acc 1 / mag 0). 모터 옆이라 mag 0 은 예상된 것이고, 중력만
필요하면 지자기를 빼는 **IMUPLUS(0x08)** 모드가 더 맞을 수 있다. A/B 미실시.

### 1.3 전류 상한 350 -> 700

| | 350 틱 | 700 틱 |
|---|---|---|
| 전류 | 0.94 A | 1.88 A |
| 토크 | 1.68 N·m | 3.36 N·m |
| 심 `effort_limit_sim` 대비 | 41% | 82% |
| **포화(>95% 천장) 스텝** | 다리 10축 중 평균 4.8축 | **0%** |

실측 최대 전류 1.447 A (가용 1.883), 온도 34~45℃. **토크 천장은 더 이상
제약이 아니다.**

## 2. 그런데 여전히 쏠린다 — 위치는 정확히 잡혔다

양발 접지 구간에서 URDF FK 로 발 링크 기울기를 재고 IMU 와 나란히 놓으면:

| | 값 |
|---|---|
| 정책이 **지령한** 발 pitch | **−2.4°** (READY 는 +4.03°) |
| 실제 발 pitch | **−21.6°** |
| 추종 오차 | **−19.3°** |
| IMU 몸통 pitch | +22.0° |
| **발 pitch + 몸통 pitch** | **+0.3°** |

마지막 줄이 중요하다. 발바닥이 지면에 평평하면 이 둘의 합이 0 이어야 하고
실제로 +0.3° 다 — **두 센서가 서로를 검증한다. 기울기는 진짜고 IMU 문제가
아니다.** 그리고 **정책은 똑바로 서라고 명령하고 있다.** 기울기는 정책의
선택이 아니라 관절이 하중에 밀린 결과다.

결정적 증거는 사람이 로봇을 들어올린 구간이다:

```
t=12-14s  접지 94%/94%   추종오차 −18.2°   몸통 +20.4°
t=14-16s  접지 21%/25%   추종오차  +1.0°   몸통  +4.0°   <- 손에 들림
t=20-22s  접지 61%/54%   추종오차 −15.3°   몸통 +17.4°
```

하중을 빼면 오차가 사라지고 자세가 정상으로 돌아온다.

부수 증상도 같은 뿌리다: 접지 스위치 토글이 왼발 17회 / 오른발 27회인데,
0.568 s 주기로 23 초면 발마다 **82회**가 나와야 한다. 몸통이 19° 처진 채 양발
앞날에 얹혀 있어 체중 이동이 안 되고 발이 지면을 긁는다.

## 3. 근거가 확실한 원인 — 속도 포화 (심에 없는 물리)

| 관절 | 지령속도 p95 | 지령 max | **실측 max** |
|---|---|---|---|
| left_knee | 4.84 | 6.30 | **3.53** |
| right_knee | 5.17 | 6.22 | **3.98** |
| left_hip_pitch | 4.66 | 6.22 | **3.72** |
| right_hip_pitch | 4.26 | 6.10 | **3.76** |

무부하 계단시험에서 같은 무릎이 **4.41 rad/s** 를 낸다(무부하 한계 4.82 의
92%). 보행 중에는 3.53 에서 막힌다. 부하가 걸리면 모터가 토크-속도 직선을
타기 때문이다:

```
ω = 4.82 × (1 − τ / 4.1)      (XM430-W350: 무부하 4.82 rad/s, 스톨 4.1 N·m)
```

각 축 최고속도 순간의 직선 사용률: left_hip_pitch **93%**, right_ankle **99%**,
right_hip_pitch 87%, left_hip_roll 85%, left_knee 81%. 반면 오차가 거의 없는
두 축(left/right hip_yaw)은 51% / 57% 다. **직선에 붙은 축이 뒤처지는 축이다.**

**심에는 이 직선이 없다.** 현재 액추에이터는 `ImplicitActuator` 이고
`effort_limit_sim = 4.1` 과 `velocity_limit_sim = 4.82` 를 **서로 독립으로**
건다. 심의 다리는 "4.1 N·m 를 내면서 동시에 4.82 rad/s 로" 움직일 수 있고,
실기는 그 조합이 물리적으로 불가능하다. 정책은 존재하지 않는 액추에이터를
전제로 걸음을 배웠다.

**게인은 문제가 아니다.** `docs/handoff/project_openduck_bam_pd_gains.md` 에
따르면 `stiffness = 37.65` 는

```
stiffness = (1/128) * kp_register(800) * vin(12.0) * max_pwm(1.0) * kt/R
```

로 **실기의 P=800 을 넣어서** BAM 실측 kt/R 로 유도한 값이다. 실기 서보에서
읽은 P/I/D 도 다리 전 축 800 / 0 / 4700 으로 일치한다. stiffness·damping·
armature·friction 은 건드릴 이유가 없다.

### 제안 (재학습 필요)

IsaacLab 에 이미 맞는 클래스가 있다 — `DCMotor` 가 정확히 그 직선을 구현한다
(`source/isaaclab/isaaclab/actuators/actuator_pd.py:299`):

```python
torque_speed_top = self._saturation_effort * (1.0 - self._joint_vel / self.velocity_limit)
```

```python
# ImplicitActuatorCfg -> DCMotorCfg
saturation_effort = 4.1      # 스톨 토크 (N·m)
velocity_limit    = 4.82     # 무부하 속도 (rad/s)
effort_limit      = 3.36     # 전류 700 틱 = 1.88 A 에 해당
# stiffness/damping/armature/friction 은 BAM 실측값 그대로
```

## 5. 틀린 것으로 판명된 이전 분석 (재발 방지용)

### 5.1 "심 강성이 실기의 2배다, P 게인을 800 -> 1600 으로"

PWM 모델(`Kp = 4.1/885 × (P/128) × 651.9 = 18.9 N·m/rad`)로 계산해 심의 37.65
와 2배 차이라고 봤다. **틀렸다** — 37.65 자체가 kp_register=800 에서 유도된
값이다(§3). **P 게인은 건드리면 안 된다.**

### 5.2 "IMU 와 다리 운동학이 18° 어긋난다 -> IMU 마운트 오프셋"

두 양을 **뺐다.** 발 pitch 는 몸통 기준 발 기울기, IMU pitch 는 세계 기준 몸통
기울기라 발바닥이 평평하면 **합이 0** 이 되는 관계다. 제대로 하니 +0.3° 로
정확히 맞는다. **IMU 마운트 오프셋 가설 폐기.**

### 5.3 "큰 오차 + 적은 전류 = 고장"

"P=800 이면 오차 1° 당 0.185 A" 를 근거로 (A) 토크 안 걸림 / (B) 기계적 막힘
이분법을 세웠다. **전제가 틀렸다** — 정상 작동하는 무릎도 무부하 계단시험에서
평균 오차 18.08° 에 전류 0.086 A, 즉 **0.0048 A/°** 로 모델의 1/38 이다. 큰
계단에서는 서보가 속도 한계로 슬루하고 그동안의 오차는 "힘이 모자라서"가
아니라 "아직 못 갔을 뿐"이라 전류를 안 쓴다.

### 5.4 offset 시험의 "18.7° 잔여오차"

`joint_step_test.py` 가 CSV 에 **클램프 전** 목표(−137.9°)를 적는데 실제 전송된
건 `tick_of` 가 URDF 한계에서 자른 −120° 였다. 진짜 목표 기준 잔여오차는
0.56~0.81°. **스크립트 로깅 버그였다.**

### 5.5 "present_PWM 이 갈라줄 것이다"

**안 갈라준다.** 전 축 통틀어 PWM 100% 인 샘플이 **59%**, 중앙값 100% 다.
전류제한 위치제어(mode 5)에서 이 레지스터는 전류 제한기를 거치기 전 위치
제어기 출력으로 보이고, D=4700 이 빠른 움직임에서 상시 포화시킨다. 역기전력
가설도 검증 실패 — 속도가 올라도 전류가 줄지 않는다(0.132 -> 0.311 A).

### 5.6 몸통 피치 부호 (선행 보고서와 이견)

`hw_v40_collapse_2026-08-10.md` 는 "뒤로 주저앉았다"로 적었다. 근거 두 개가
반대를 가리킨다:

1. t=0.04(램프인 직후 READY)에서 IMU 공식 +2.3°, 다리 운동학 +2.0° 로 일치하고,
   `joystick_env_cfg.py` 주석이 그 자세를 "몸통이 4도 **앞으로** 기운다"로
   규정한다. 반대 부호면 레포 자기 주석과 어긋난다.
2. 사용자 직접 관찰이 "앞으로 계속 쏠린다"다.

원인 A·B·C 판정은 부호와 무관하지만, 앞쏠림 추적과 같은 현상인지 갈리는
지점이라 기록해 둔다.
