## 1. 관절별 추종 오차 — 한쪽만 못 따라간다

목표각(`target_*`) 대비 다음 스텝의 실제 각(`pos_*`)을 정착 구간(t > 2 s)에서
비교했습니다.

| 관절 | 평균 오차 | RMS | 최대 |
|---|---:|---:|---:|
| left_hip_yaw | +0.10° | 0.18 | 0.63 |
| left_hip_roll | +1.02° | 1.07 | 1.44 |
| **left_hip_pitch** | **−7.30°** | **7.33** | **−9.82** |
| left_knee | −2.95° | 3.07 | −3.77 |
| left_ankle | −0.99° | 1.02 | −1.37 |
| right_hip_yaw | −0.18° | 0.24 | −0.66 |
| right_hip_roll | +1.18° | 1.22 | 1.54 |
| **right_hip_pitch** | **−0.12°** | 0.21 | 0.66 |
| right_knee | +1.39° | 1.44 | 1.73 |
| right_ankle | +0.13° | 0.20 | 0.65 |

평균 ≈ RMS ≈ 최대인 것에 주목할 만합니다 — 진동이 아니라 **일정한 편차**입니다.
그리고 좌우 대칭 관절인 `right_hip_pitch` 는 0.12° 로 거의 완벽합니다. 같은 모델의
같은 서보가 한쪽만 7.3° 못 따라간다면 모터 성능 문제로 보기 어렵습니다.

## 2. 원인 — 소프트웨어 클램프

`left_hip_pitch` 의 목표와 실제를 시간축으로 보면 답이 나옵니다.

| t (s) | L 목표 | L 실제 | R 목표 | R 실제 |
|---:|---:|---:|---:|---:|
| 0.04 | 50.7° | 51.6° | 55.9° | 53.3° |
| 1.74 | **80.7°** | 69.7° | 47.6° | 48.2° |
| 5.18 | **77.0°** | 69.8° | 43.3° | 43.2° |
| 9.43 | **76.9°** | 69.8° | 43.3° | 43.2° |

실제 각이 **69.7~70.0° 에 붙어 있습니다.** `robot/robot.urdf` 의 `hip_pitch`
한계가 −30° ~ **+70°** 이고, 실기 코드(`rustypot_hwi.tick_of`)가 goal position 을
tick 으로 바꿀 때 이 범위로 클램프합니다.

즉 **−7.3° 는 모터가 못 간 거리가 아니라 우리가 잘라낸 양**입니다. 모터는 자기가
받은 70° 를 정확히 지키고 있습니다.

> 시뮬 쪽 URDF 도 같은 −30° ~ +70° 임을 확인했습니다 (데스크탑 `robot/robot.urdf`
> 직접 파싱). 한계값 자체는 양쪽이 일치합니다.

## 3. 진짜 문제 — 좌우 27° 비대칭

클램프는 증상을 가린 것이고, 그 아래에 있는 것은 **정책이 내놓는 비대칭한 자세**
입니다.

```
target = default_joint_pos + action × 0.25
왼쪽 : 77.0° = 51.3° + action×0.25  ->  action ≈ +1.79
오른쪽: 43.3° = 53.4° + action×0.25  ->  action ≈ −0.73
```

`default_joint_pos` 는 좌우가 2.1° 밖에 차이 나지 않는데(51.3° vs 53.4°),
**정책 출력이 좌우로 크게 갈립니다.** 결과적으로 왼다리는 한계까지 접히고
오른다리는 펴진 자세가 됩니다.

참고로 합성 정지 관측(모두 0, 접지 1,1, 위상 (1,0))을 ONNX 에 그냥 넣으면
|action| 최대가 0.93 입니다. 실기 폐루프에서 1.79 까지 커진다는 것은 관측
피드백을 타고 더 극단으로 밀려간다는 뜻입니다.

## 4. 몸통 기울기 — 측정값과 해석의 한계

`projected_gravity` (가속도계 기반, 수직이면 (0,0,−1)) 로 계산했습니다. 자이로는
각속도라 절대 기울기를 못 냅니다.

| | 값 |
|---|---:|
| 평균 기울기 | **7.0°** |
| 범위 | 0.4° ~ 26.8° |
| 평균 `projected_gravity` | (+0.108, −0.026, −0.991) |

앞뒤(x) 성분이 지배적이고 좌우(y)는 노이즈 수준입니다. 시간축으로 보면 램프인
직후에는 2~3°(거의 수직)이다가 **정책이 돌기 시작한 1초 이내에 6~8° 로 올라가
그 뒤 10초 내내 유지**됩니다. 두 번의 독립 실행에서 평균 7.0° 로 같았습니다.

**⚠️ 이 수치를 시뮬의 몸통 피치와 직접 비교하면 안 됩니다.** 시뮬 수치(v34c10
+8.19°)는 바닥에 서 있는 상태이고, 이 측정은 **사람이 손으로 받쳐 발만 살짝
닿게 한 상태**입니다. 매달린 몸은 무게중심이 이동하면 지지점 기준으로 회전하므로
기울어짐의 발생 기전 자체가 다릅니다. (초기 분석에서 두 수치의 일치를 근거로
삼았다가 정정했습니다.)

**3절의 비대칭이 이 기울기의 원인인지도 이 데이터로는 판정할 수 없습니다.**
정착 후 두 값 모두 사실상 상수이기 때문입니다 — 기울기 6.4° ± 1.6°, hip_pitch
좌우차 26.0° ± 1.4°. 변동 상관은 +0.06 이지만 둘 다 상수인 이상 이 값은 노이즈만
재는 것이라 인과를 부정하는 근거가 못 됩니다. 축도 어긋납니다: 좌우차는 좌우
비대칭이고 기울기는 앞뒤(pitch)이며, 앞뒤에 직접 대응하는 양다리 평균 굽힘은
READY 52.4° → 실측 56.5° 로 4° 차이에 그칩니다.

무엇보다 **몸통 자세를 실제로 결정하는 것이 사람 손일 수 있다**는 교란이 남아
있습니다. 가리려면 손을 떼고 재야 합니다 — 고정 지지대에 매달거나 바닥에 세운
상태에서 같은 측정을 하면 정책 기여분과 지지 조건을 분리할 수 있습니다.

## 5. 같은 세션에서 실기 쪽에 적용한 수정

기울기/비대칭과 별개로, 보고서 6절이 지적한 제어 주기 문제를 포함해 실기 쪽에서
고친 것들입니다. 모두 `AkimaraYouki/SummerProject` 의 `scripts/hw/` 에 반영돼
있습니다.

**① FTDI `latency_timer` 16 ms → 2 ms** — 가장 큰 원인이었습니다. U2D2 가 기본
16 ms 로 잡혀 있었고, 이것이 "버스 물리 한계"로 보였던 SyncRead 고정비용의
정체였습니다. udev 규칙(`/etc/udev/rules.d/99-ftdi-latency.rules`)으로 영구화.
1 ms 까지 낮추면 응답 패킷이 쪼개져 도착하는 빈도가 크게 늘어 2 ms 로 절충했고,
읽기 재시도 예산도 2 → 6 회로 올렸습니다.

**② 발 접촉 스위치 좌우 반전** — GPIO 29=left/31=right 로 가정했으나 실제 배선은
반대였습니다. 관측 `obs[97:99]` 가 10초 내내 좌우 뒤바뀐 채 들어가고 있었습니다.

**③ Input Voltage Error 자동 복구** — 루프가 빨라진 뒤 램프인 직후 여러 축(매번
다른 조합)에 `hw_error_status` bit0 가 래치되는 현상이 재현됐습니다. 전압을 재보면
14축 모두 11.7~11.8 V 로 정상이라, 다축 동시 가감속의 역기전력 스파이크로 추정
합니다. bit0 단독인 축만 `reboot` 후 재설정하고 계속 진행하도록 했습니다
(과열/과부하/전기충격/인코더 비트가 섞이면 종전대로 정지).

**④ 액션 저역필터 옵션(`--action-lpf-alpha`)** — 보고서 실험 A 를 그대로 구현.
`target` 계산에만 걸고 `last_act`(관측 이력)은 raw 를 유지합니다(v35 는 무필터로
학습됐으므로). vx/vy/wz 가 0 이 아니면 경고를 찍습니다.

**결과 (α = 0.5, 정지 10초)**

| 지표 | 이전 | 현재 |
|---|---:|---:|
| 루프 평균 주기 | 27.8 ms | **21.6 ms** |
| 루프 지터 (표준편차) | 12.3 ms | **5.85 ms** |
| 최대 주기 | 64.8 ms | 44.2 ms |
| 몸통 각속도 \|ω\| 평균 | 0.2592 rad/s | **0.0983** (−62 %) |
| 액션 방향 반전 비율 | 68.3 % | **56.3 %** |
| 하드웨어 에러 | 매 실행 발생 | 0 회 |

지터가 절반 이하로 줄었고 떨림 지표도 크게 개선됐습니다. 다만 **기울기(7.0°)와
좌우 비대칭은 이 수정들 전후로 변하지 않았습니다** — 타이밍이나 하드웨어가 아니라
정책 쪽 특성이라는 근거이기도 합니다.

## 6. 확인이 필요한 것

- **시뮬에서도 `left_hip_pitch` 가 70° 에 포화하는지.** 실기와 같은 정지 조건에서
  `target` 과 실제 관절각을 찍어보면 바로 갈립니다. 시뮬도 포화한다면 sim2real
  격차가 아니라 정책이 도달 불가능한 자세를 학습한 것이고, 시뮬은 여유가 있다면
  (PhysX 한계 처리 방식 차이 등) 그쪽이 격차의 후보입니다.
  - 참고로 실기와 시뮬의 한계 **처리 방식**은 다릅니다. 시뮬은 PD 목표가 77° 인
    채 PhysX 가 70° 에서 물리적으로 막아 **한계에 계속 밀어붙이는** 상태가 되고,
    실기는 goal position 자체를 70° 로 잘라 보내 **미는 힘 없이 그 자리에 서는**
    상태가 됩니다. 같은 각도라도 접촉력/전류가 다릅니다.
- **`hip_pitch` 70° 가 실기 실제 가동범위보다 보수적인지.** README 의 "남은 일"
  에도 "`right_hip_pitch` 가 레퍼런스에서 URDF 한계를 4° 넘는다 / 실기 가동범위를
  재보거나" 로 이미 올라와 있는 항목입니다. 실기가 더 굽혀지는데 막고 있는 것이면
  정책이 의도한 자세를 아예 만들지 못하고 있는 셈입니다.
- **v36 의 정지 좌우대칭 벌점이 이 27° 비대칭을 잡는지.** 실기에서 관측된 이
  증상이 v36 이 노리는 바로 그 문제로 보입니다. 학습 완료(현재 2000/3000) 후
  같은 절차로 재측정하면 직접 비교됩니다.

매 스텝 `~/rl_walk_log.csv` 에 기록됩니다: 14축 `pos_*` / `vel_*` / `action_*` /
`target_*`, `contact_l/r`, `gyro_*`, `accel_*`, `proj_grav_*`, `phase_cos/sin`.
본문 수치는 전부 이 파일에서 계산했습니다.

- 추종 오차 = `pos_*[i+1] − target_*[i]` (목표를 쓴 다음 스텝의 실제값), t > 2 s
- 기울기 = `acos(−proj_grav_z)`
- 액션 방향 반전 = 연속 두 스텝의 액션 차분 부호가 뒤집힌 비율 (다리 10축 평균)
